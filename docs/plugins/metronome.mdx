title: "Metronome"
description: "Export token and external Fish Audio usage from the Regali fork"

Metronome is an opt-in **builtin plugin** in the REGALITECH fork. It exports
successful Chat Completions, Text Completions and Responses usage, including
completed streams, as `token-billing` events. Authenticated external Fish Audio
reports produce `fishaudio-usage` events.

## Build and configure

The normal gateway build includes the plugin. `transports/Dockerfile.local`
continues to build a statically linked gateway; no shared library or separate
plugin build is required. The release workflow starts each architecture's image
in dry run and checks `/api/plugins/loaded` before publication.

```sh
make setup-workspace
make build LOCAL=1
make test-metronome
```

Open **Plugins → metronome** to save configuration and enable or disable the
plugin. It remains a builtin (`isCustom: false`); no install, path, or shared
library is needed. If there is no saved entry yet, the page offers a disabled
configuration with `api_key: "env.METRONOME_API_KEY"` and `dry_run: true`.

The page uses the common `GET /api/plugins`, `GET /api/plugins/metronome` and
`PUT /api/plugins/metronome` APIs. Saving the Metronome JSON sends
`replace_config: true`: the full object replaces the stored config. Other API
clients retain the existing merge behavior unless they explicitly opt into
replacement. Omission alone in a merge request does not delete a stored field.

`enabled` is the saved desired state. Check the runtime status, logs and
`loaded` flag too: initialization failure returns an error, even though the
configuration has been saved. A failed reload can leave the previous instance
running with its old configuration; the page reports this in the logs. Save
again to retry, or disable the plugin. `active` confirms initialization, not
successful delivery or matching of billing events.

For a file-managed installation, the example in
`examples/configs/withmetronome/config.json` can still bootstrap the plugin:

```json
{
  "name": "metronome",
  "enabled": true,
  "version": 1,
  "config": {
    "dry_run": true,
    "api_key": "env.METRONOME_API_KEY"
  }
}
```

For UI-managed operation, remove only Metronome's entry from the startup file
and retain the default config-DB merge mode. Do not select
`config.source_of_truth: "config.json"`. Other plugin entries can remain.
UI saves preserve the stored `version`; no Terraform edit or version bump is
needed for daily operations. File-managed installations still need a higher
`version` to overwrite stored settings, including enable/disable.

For ETLA, `etla_infra_tf/stack/modules/bifrost` supplies credentials independently
of runtime enablement and no longer renders Metronome into the startup file.
Set `bifrost_metronome_secret_enabled = true` once when adopting UI management.
The existing API key is plaintext in AWS Secrets Manager at
`etla/metronome/api_key`. External Secrets syncs it to Kubernetes Secret
`bifrost-metronome` / `api-key`, injected as `METRONOME_API_KEY`.
Only an `env.NAME` reference is accepted for `api_key`; literal keys are rejected
before a config-DB write. Resolution through `SecretVar` happens during plugin
initialization and keeps the value in process memory. The config DB and management
responses retain only the environment reference. Disabled saves do not require
the environment variable to be populated. Terraform does not read or store the
key value. Live deployment waits for the ExternalSecret to become ready; dry run
needs no key.

Secret registration does not prove that a running process received the key.
When live initialization reports an unset or empty variable, check the selected
deployment revision, Pod `secretKeyRef` name/key, ExternalSecret `Ready` status,
and whether the variable is nonempty in the Bifrost process, without displaying
its value. After Secret rotation or adding env injection, restart the Pods through
the normal deployment process; an in-process plugin reload cannot refresh a Pod's
environment from Kubernetes.

To verify a locally built release image:

```sh
docker build -f transports/Dockerfile.local -t bifrost-metronome .
bash .github/workflows/scripts/test-metronome-image.sh bifrost-metronome
```

## Customer identity

Both token and external Fish Audio events use the **authenticated Bifrost
governance virtual-key UUID** directly as `customer_id`. Register this UUID in
the intended Metronome customer's `ingest_aliases`. Use the UUID in the virtual-key
management view, not the secret `sk-bf-...` value passed in `x-bf-vk`.
No per-customer routing table is configured in Bifrost.

For example, create a Metronome customer for tenant A, add tenant A's VK UUID as
an ingest alias, and attach a contract using the shared rate card. Repeat for
tenant B with its own VK and customer. The aliases resolve on the Metronome side;
Metronome's generated customer UUID remains the ID used by management APIs.
Customer/contract provisioning can be manual and does not require a Bifrost
governance Customer or Team for this integration.

The exporter reads the UUID only from authenticated governance context. Raw keys,
arbitrary caller headers and submitted customer/tenant dimensions cannot select
the billing customer. Missing or blank authenticated IDs skip token export with
a warning and fail external audio delivery. The exporter does not query Metronome
to check aliases: ingest acceptance does not establish that the intended customer
or metric matched. Verify matching before relying on usage or invoice totals.

Multiple VK UUIDs can be registered as aliases on the same Metronome customer.
When replacing a VK, add the new UUID to that customer and retain old aliases for
historical usage and retries. Never reassign an old alias to a different tenant.
The [setIngestAliases API](https://docs.metronome.com/api-reference/customers/create-or-update-customer-ingest-aliases)
replaces the complete alias set, so include existing aliases when updating it.

### Migrate from customer mappings

This changes the usage event's customer identifier. Before enabling the new version:

1. Register each existing VK UUID as an ingest alias on its existing Metronome
   customer, preserving other aliases. Check keys previously using the token-only
   fallback individually so usage stays with the intended tenant.
2. Empty `customer_mapping` (`{}` or `null`) and `default_customer_id` (`""` or
   `null`) are accepted at initialization and removed on the next configuration
   save. Populated or malformed values remain stored and block initialization;
   they are never silently discarded.
3. After migrating populated mappings, explicitly remove those fields in the
   Plugins JSON editor and save. API clients must send the full desired config
   with `replace_config: true`. A normal merge request retains omitted fields.
   File-managed installations instead need a higher configuration `version`
   and a restart. Select an image containing this management support first.
4. Send fresh usage from two tenant keys and inspect each event's matched customer
   and billable metrics, then verify each customer's draft invoice.

External transaction IDs remain based on the VK UUID and original request ID.
Do not regenerate IDs or timestamps when replaying a saved report during migration.

## Enable sandbox delivery later

1. Register at https://signup.metronome.com/ and complete the emailed login flow.
2. In the sandbox, create a customer and register the tenant's Bifrost virtual-key
   UUID as an ingest alias. The UUID comes from the virtual-key management view.
3. Create a rate card and customer contract. For a manual first experiment, make
   four SUM billable metrics filtered by `event_type = token-billing`, measuring
   `input_tokens`, `output_tokens`, `cached_input_tokens`, `cached_write_tokens`.
   Add `model` and `provider` as group keys before saving the metrics. Create
   usage products and rates using those keys, and attach the rate card to the
   customer contract. Event ingestion alone does not create pricing or contracts.
4. Use the mapping-free plugin configuration above. No customer ID is stored in it.
5. Put a **sandbox** API key in the Bifrost process environment as
   `METRONOME_API_KEY`, referenced by `api_key: "env.METRONOME_API_KEY"`. For Docker, pass
   the environment variable into the container. Do not put secrets in config JSON.
6. Set `dry_run: false`, enable the plugin and save in the Plugins page. Missing
   credentials cause initialization to fail visibly with the environment name.
7. When ready for a later integration check, make a normal gateway request using
   the virtual key whose UUID was registered as an alias, then inspect Metronome
   Events and the draft invoice.

The API hostname is shared between sandbox and production; the API key determines
the instance. This plugin cannot infer the instance from an opaque API key.

## Model mapping

Rates and events must use the same model/provider strings. The default adds the
provider prefix to unqualified models, e.g. `openai` + `gpt-example` becomes
`openai/gpt-example`. It does not fetch a price catalog. For Vertex, Bedrock,
Azure, aliases or self-hosted providers, set explicit mappings to your rate card:

```json
{
  "model_mapping": { "vertex/example-model": "google/example-model" },
  "provider_mapping": { "vertex": "YOUR_RATE_CARD_PROVIDER_VALUE" }
}
```

Model aliases and server-side fallback metadata are resolved before mapping.
Bifrost's input count includes cached tokens; the exporter subtracts cache reads
and writes from ordinary input tokens and emits them as separate properties.
Prompt, response text, raw virtual keys and provider/API secrets are never part
of an event. Dry-run logs include the customer ID and usage metadata.

## Prototype boundaries

- No pricing changes, contract/customer provisioning, Stripe payment setup or
  database migration is performed by the plugin.
- Direct Fish TTS, STT, WebSocket Realtime, embeddings, images,
  failed/cancelled requests and semantic-cache hits are excluded in this first
  LLM prototype. Advanced token categories (audio/image/cache TTL/tier) are not
  separately priced by this four-counter event format.
- Only completed streams with usage on the final hook are exported. Missing or
  inconsistent usage is not estimated. Cancellation billing and provider-specific
  final-usage behavior need integration checks before production use.
- For token events, a bounded in-memory queue keeps HTTP calls out of the hook. Up to three attempts
  reuse the identical payload and transaction ID for network errors, 429 and 5xx.
  Other HTTP errors are logged without retry. A fresh gateway request gets a new
  event ID, even if it is an application-level retry.
- For token events there is no durable outbox: queue overflow, retry exhaustion, process failure
  or shutdown exceeding five seconds can lose events. This is a sandbox prototype,
  not a production billing ledger. Existing Bifrost governance remains active.

API reference: https://docs.metronome.com/api-reference/usage/ingest-events

Tests cover token accounting, instance isolation, secret references, audio
conversion, HTTP retries, builtin loading, and the real handler/exporter path.
The `Metronome Tests` PR workflow runs these without credentials or a skip flag.
Live Sandbox ingestion is a separate validation step.

## External Fish Audio usage prototype

The transport resolves only the configured `metronome` plugin for each report.
After input validation, governance authentication and the existing accounting /
logging hooks, it calls the builtin instance’s `ReportFishAudio` method with
validated typed usage. There is no HTTP header acknowledgment contract.
It does not run other HTTP/LLM plugins or make a provider call. No new core types,
provider methods, plugin-loader support, or database migrations are needed.

### Request and acknowledgment

`POST /v1/fishaudio/usage` requires both `x-request-id` and `occurred_at` only
when Metronome is enabled and loaded. The timestamp is RFC3339 actual occurrence
time, retained across retries. Both remain optional for legacy logging-only
reports; Bifrost generates a request ID when omitted. The transcription usage
endpoint is unchanged because this plugin does not export transcription. The
body is otherwise unchanged; unknown fields are still rejected.

```json
{
  "billable_bytes": 54,
  "audio_ms": 2500,
  "outcome": "completed",
  "turn_id": "turn-1",
  "sub_id": "sub-1",
  "model": "s2-pro",
  "occurred_at": "2026-09-15T06:00:00Z"
}
```

Unlike queued token events, audio reports wait for Metronome's HTTP 200 before
returning 202. Up to three identical requests are attempted for network errors,
429 and 5xx, with a 12-second overall deadline and 3-second per-attempt timeout.
An ingest error, missing authenticated virtual-key ID, shutdown, or configured plugin that
failed to initialize returns 503. The caller must retain and retry its event.
There is no server-side background retry after a failed external report.

A successful response includes `metronome_status: "sent"` and `transaction_id`.
Dry run returns `metronome_status: "dry_run"`; it does not contact Metronome.
When the plugin is absent or disabled the endpoint retains its logging-only
behavior and omits these fields. **202 without `metronome_status: "sent"` does
not confirm Metronome delivery.** Ingest acceptance also does not prove that a
customer, billable metric, or invoice matched; verify those in Sandbox.

The Metronome plugin uses the authenticated governance VK UUID as the customer
ingest alias, including for audio dry run. Do not use a caller header, secret VK
value, or submitted customer field as the billing identity. Register the reporting
key's UUID as an alias on the intended Sandbox customer before sending live usage.
These instructions do not change any live aliases or credentials.

### Event and pricing

`fishaudio-usage` properties contain numeric `billable_bytes` (UTF-8 input bytes,
not characters or audio file size), numeric `audio_ms`, string `outcome`,
`provider`, `model`, `turn_id`, `sub_id`, `usage_source: "external"`, and
`schema_version: 1`. Model/provider mappings also apply to these events. No text,
audio bytes, secret headers, or arbitrary caller dimensions are forwarded.

The plugin preserves all four outcomes (`completed`, `barged_in`, `failed`,
`cache_hit`) and zero quantities. It does not infer free usage from an outcome or
estimate missing quantities. A failed or interrupted generation may still have
billable bytes. For cached playback without new generation, submit zero bytes.
Define whether `audio_ms` measures generated or actually played audio in the
reporting application; the exporter preserves the reported measurement.

Create a SUM metric for `billable_bytes`, filtered by `fishaudio-usage`. Initially
keep `audio_ms` as an observation unless the commercial model explicitly charges
for duration too. Define provider/model group keys and the rate card / customer
contract before sending test events. This plugin does not create them.

### Retry guarantees and prototype limits

Token events identify an actual inference attempt (a fresh UUID), while external
reports identify an already completed event (the caller’s saved request ID).
Using the caller ID for token events would collapse separate billable inference
attempts. Both event types use the same generic event envelope.

The external transaction ID is SHA-256 of the JSON array
`["bifrost", "fishaudio-usage", authenticated_vk_uuid, x_request_id]`, prefixed
with `bf-fishaudio-`. It stays stable across identical client retries and process
restarts; the caller-supplied timestamp is normalized to UTC, never regenerated.
Metronome deduplicates the transaction ID within its 34-day window:
https://docs.metronome.com/api-reference/idempotency

- Save the event **before** sending and resend exactly the same file. Do not
  rotate the VK UUID, reassign its customer alias, or change model mappings while replaying events.
- Reusing an ID with changed quantities is not a correction: this prototype has
  no durable receipt ledger or payload-conflict detection. Metronome can ignore
  the changed event. Do not use this interface for adjustments.
- Keep historical timestamps intact. Metronome accepts up to 34 days of backfill;
  older usage needs a separate operational process.
- The local logging/governance hooks finish before delivery. A 503 can therefore
  coexist with a usage log / budget update. Logging is asynchronous, so 202 is
  not a durable-log acknowledgment. Governance's approximately 5-minute in-memory
  deduplication does not guarantee unique local budget updates after restart or
  across Pods. The stable ID protects Metronome metering, not those local counters.
- Outbox persistence, durable local accounting deduplication, conflict detection,
  and billing reconciliation remain follow-up work for production use.

### Local test and Sandbox verification

Build the gateway (see above), register the reporting VK UUID as a Sandbox
customer ingest alias, and restart with the Sandbox key in the process environment.

Send a usage report to `POST /v1/fishaudio/usage` using the request format above,
with `x-bf-vk` and a stable `x-request-id`. Save the payload, including
`occurred_at`, before sending and reuse it unchanged when checking deduplication.

After `metronome_status: "sent"`, query `/v1/events/search` with
`{"transactionIds": ["<returned transaction_id>"]}` using the Sandbox key.
Check `matched_customer`, `matched_billable_metrics`, and `is_duplicate`, then
verify that metric/invoice quantities match the submitted report; replay must
not increase billable quantity. Also test missing authenticated IDs, inactive VK, interrupted
outcomes, and delivery failure. Search API reference:
https://docs.metronome.com/api-reference/usage/search-events
